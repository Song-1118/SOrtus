## 一、总则

### 1.1 目的

统一 SOrtus 项目在**代码、资源、文档、Git、版本、发行**六个方面的协作方式，做到：

- 任何人接手都能按同一套目录找到所需资源
- 提交记录可读、可追溯、可回退
- 每个发行版都可被精确还原
- 开源协作时外部贡献者能快速理解规则

### 1.2 基本原则

1. **约定优于配置**：先遵守本文档，再谈个性化。
2. **单一可信源**：同一类信息只在一个目录维护，其他处引用链接。
3. **可追溯**：所有产出（代码、文档、图片、版本）都能对应到具体提交。
4. **本地优先**：不依赖任何远端服务完成开发流程。
5. **最小惊讶**：目录、命名、提交、版本都按行业通用惯例。

### 1.3 技术栈约定（不可变更，除非走评审）

`.NET 10 LTS + C# 14 + WPF + SQLite`，目标平台 Windows x64，MIT 许可证。

## 二、目录结构规范

### 2.1 仓库根目录

仓库根目录保持精简，只放与"整个项目"相关的内容，不放具体业务代码与素材。

```
SOrtus/
├── .gitignore                      # Git 忽略规则
├── .gitattributes                  # 换行符、语言统计等 Git 属性
├── LICENSE                         # MIT 许可证（必须存在）
├── README.md                       # 项目入口说明（项目简介、构建、运行、贡献指引）
├── README.zh-CN.md                 # 中文 README（多语言项目主文档之一）
├── README.en-US.md                 # 英文 README
├── SOrtus.sln                      # 解决方案文件
├── Directory.Build.props           # 全局构建属性（版本号、警告级别等）
├── build/                          # 构建与打包脚本
├── docs/                           # 项目文档（开发、设计、产品）
├── resources/                      # 项目级资源（图标、字体、占位图等）
├── samples/                        # 示例数据 / 示例截图（可选）
├── src/                            # 源码
└── tests/                          # 测试代码
```

**根目录禁止出现**：编译产物（`bin/`、`obj/`）、临时文件、个人笔记、单个功能截图、与项目无关脚本。

### 2.2 源码目录 `src/`

```
src/
├── SOrtus/                         # 主程序（WPF 桌面应用）
│   ├── App.xaml / App.xaml.cs      # 应用入口
│   ├── MainWindow.xaml(.cs)        # 主窗口
│   ├── Views/                      # 视图（XAML 界面）
│   │   ├── Project/
│   │   ├── Clip/
│   │   ├── Todo/
│   │   └── Settings/
│   ├── ViewModels/                 # 视图模型（MVVM）
│   ├── Models/                     # 数据模型与实体
│   ├── Services/                   # 业务服务（立项管理、Git、提醒等）
│   ├── Repositories/               # 数据访问（SQLite）
│   ├── Resources/                  # 应用内资源（样式、主题、资源字典）
│   │   ├── Themes/
│   │   ├── Styles/
│   │   └── Strings/                # .resx 多语言资源
│   ├── Controls/                   # 自定义控件
│   ├── Converters/                 # 值转换器
│   ├── Behaviors/                  # 交互行为
│   ├── Migrations/                 # 数据库迁移脚本
│   └── Assets/                     # 应用打包资源（图标、安装背景等）
└── SOrtus.Core/                    # 可选：可复用核心库（实体、接口、服务契约）
```

分层职责：

| 层 | 职责 | 禁止 |
| --- | --- | --- |
| Views | 界面呈现、用户交互 | 写业务逻辑、直接访问数据库 |
| ViewModels | 状态、命令、数据绑定 | 写持久化逻辑 |
| Services | 业务逻辑、外部操作（Git、提醒） | 依赖具体 UI 控件 |
| Repositories | 数据读写、SQLite 操作 | 写业务规则 |
| Models | 数据实体、枚举、常量 | 包含 UI 或持久化代码 |

## 三、图片资源管理

### 3.1 总体原则

- **源码用图与应用资源图分离**：源码里编译进程序集的图标/样式图放 `src/SOrtus/Assets/`；项目宣传、文档配图、设计稿放 `resources/` 或 `docs/`。
- **禁止散放**：不允许在根目录、`src/` 任意位置、`docs/` 任意子目录随意放图片。
- **原始素材与导出产物分离**：设计源文件（`.psd`/`.fig`/`.sketch`/`.xaml` 源）与导出图分目录存放。
- **图片纳入 Git 版本管理**，但仅限最终产物；大型二进制源文件（超过 10MB）建议不入仓，改用外部说明文件引用。

### 3.2 目录结构

```
resources/
├── icons/                          # 图标（应用图标、文件类型图标、功能图标）
│   ├── app/                        # 应用图标（多分辨率：16/32/48/64/128/256/512）
│   ├── ui/                         # 界面功能图标
│   └── source/                     # 图标设计源文件
├── images/                         # 图片素材
│   ├── logo/                       # 项目 Logo（横版/竖版/单色/反白）
│   ├── illustrations/              # 插画、空状态图、引导图
│   └── source/                     # 图片设计源文件
├── screenshots/                    # 应用截图（README、文档、发行说明用）
│   ├── v0.1.0/                     # 按版本归档
│   ├── v0.2.0/
│   └── latest/                     # 最新版截图（随版本更新覆盖，但历史保留在版本目录）
└── themes/                         # 主题相关视觉资源（壁纸、渐变素材等）

docs/
├── images/                         # 文档专用配图（流程图、架构图、示意图）
│   ├── arch/                       # 架构图
│   ├── flow/                       # 流程图
│   └── ui/                         # 界面设计稿
```

### 3.3 图片格式规范

| 用途 | 推荐格式 | 说明 |
| --- | --- | --- |
| 应用图标、功能图标 | `.png`（透明）+ `.svg` 源 | 图标需提供多分辨率 |
| 应用主图标 | `.ico`（含多尺寸） | Windows 安装与任务栏使用 |
| 截图、照片 | `.png`（无损）/ `.jpg`（照片） | 截图一律 PNG |
| 文档配图、插画 | `.png` / `.svg` | SVG 优先，便于缩放 |
| 设计源文件 | 原始格式（`.psd`/`.fig` 等） | 可放 `source/`，大文件不入仓 |

### 3.4 图片命名规范

格式：`<用途>_<内容>_<状态或尺寸>.<扩展名>`，全小写，单词间用连字符 `-` 连接。

```
✅ 正确
app_icon_256.png
app_icon.ico
ui_icon_git_commit_24.png
ui_icon_git_commit_48.png
logo_horizontal_color.png
logo_vertical_monochrome.png
screenshot_main_window.png
doc_arch_layered.png

❌ 错误
图标1.png
截图2026-01-01.png
微信图片.png
new_icon_final_v2.png
```

**特殊规则**：

- 图标按尺寸后缀命名（`_16`/`_24`/`_48`/`_256`），不把尺寸写进目录名
- 版本化截图放版本目录，文件名不必带版本号
- `latest/` 目录截图可同名覆盖，但每个版本目录必须保留一份快照

### 3.5 图片引用规范

- 文档引用图片统一使用**相对路径**：`![架构图](images/arch/layered.png)`
- README 引用截图：`![主界面](resources/screenshots/latest/screenshot_main_window.png)`
- 应用内图片引用统一走 `Pack URI`：`pack://application:,,,/Assets/...`
- 禁止引用本地绝对路径、网络图床（除非文档明确允许外部链接）

## 四、文档管理

### 4.1 文档总目录 `docs/`

```
docs/
├── README.md                       # 文档索引（导航到各文档）
├── 开发文档.md                     # 技术架构、设计决策
├── 产品需求文档.md                 # PRD
├── 版本迭代规划.md                 # 版本路线与验收
├── 项目开发规范.md                 # 本文档
├── 数据库设计.md                   # 表结构、字段、迁移说明
├── 用户使用说明.md                 # 面向最终用户
├── 贡献指南.md                    # CONTRIBUTING（外部贡献者用）
├── 变更日志.md                    # CHANGELOG（按版本记录变更）
└── images/                         # 文档配图（见 3.2）
```

### 4.2 文档分类与归属

| 类别 | 存放位置 | 主要读者 | 更新时机 |
| --- | --- | --- | --- |
| 技术文档 | `docs/开发文档.md`、`docs/数据库设计.md` | 研发 | 架构/表结构变更时同步 |
| 产品文档 | `docs/产品需求文档.md` | 产品、研发 | 需求变更时同步 |
| 流程文档 | `docs/版本迭代规划.md`、`docs/项目开发规范.md` | 全员 | 流程调整时同步 |
| 用户文档 | `docs/用户使用说明.md`、`README*` | 最终用户 | 功能发布时同步 |
| 协作文档 | `docs/贡献指南.md`、`CHANGELOG.md` | 贡献者 | 每次发版时同步 |

### 4.3 文档格式与语言

- **默认格式**：Markdown（`.md`），便于 Git 管理与多语言协作
- **允许格式**：`.md` 为主，复杂排版（如正式对外 PDF）可另出，但需保留 `.md` 源
- **多语言**：用户向文档提供中文（`zh-CN`）与英文（`en-US`）；代码注释默认英文；文档正文中文为主，专业术语保留英文
- **单一语言源**：若同一内容有中英两版，以英文版为权威源，中文版保持同步，不得长期偏离

### 4.4 文档维护规则

- **谁改功能，谁更文档**：代码合并前必须检查相关文档是否需要同步更新
- **禁止文档漂移**：PR 中若改动架构、接口、表结构、流程，必须同步修改对应文档，否则不得合并
- **过时即删或标记**：不再适用的内容要么更新、要么删除、要么加 `> ⚠️ 已废弃，见 xxx` 说明，禁止留空段落与占位符长期存在
- **图片随文档归档**：文档配图必须与文档同仓、同目录树下，不外链

### 4.5 文档模板

每个新文档必须含以下元数据（放在文档开头）：

```markdown
# 文档标题

> 版本：v1.0
> 文档类型：（开发文档 / PRD / 规范 / 使用说明）
> 适用范围：（适用对象与边界）
> 最后更新：YYYY-MM-DD
> 维护者：（负责人或团队）
```

`CHANGELOG.md` 遵循 [Keep a Changelog](https://keepachangelog.com/) 格式，按版本记录 Added / Changed / Fixed。

## 五、命名规范

### 5.1 文件与目录

- 目录、代码文件使用**大驼峰** `PascalCase`：`ProjectWizard.xaml`、`GitService.cs`
- 文档使用**中文或英文描述性名称**：`开发文档.md`、`产品需求文档.md`
- 测试文件后缀 `Tests`：`ProjectServiceTests.cs`
- 目录名不含空格、不含特殊字符（`\ / : * ? " < > |`），统一用 ASCII

### 5.2 代码命名（C# 约定）

| 对象 | 规范 | 示例 |
| --- | --- | --- |
| 类、接口、枚举、结构体 | 大驼峰 | `ProjectWizardViewModel` |
| 接口 | 大驼峰，前缀 `I` | `IProjectRepository` |
| 方法、属性、事件 | 大驼峰 | `CreateProject()`、`ProjectName` |
| 私有字段 | 大驼峰 + 前缀 `_` | `_currentProject` |
| 局部变量、参数 | 小驼峰 | `projectName` |
| 常量 | 大驼峰 | `MaxProjectNameLength` |
| 枚举值 | 大驼峰 | `ProjectType.Programming` |
| 异步方法 | 以 `Async` 结尾 | `SaveAsync()` |

### 5.3 数据库命名

- 表名、字段名**大驼峰**，单数形式：`Project`、`CreatedAt`
- 主键统一 `Id`
- 外键命名 `<目标表>Id`：`ProjectId`
- 时间字段以 `At` 结尾：`CreatedAt`、`UpdatedAt`、`DueTime`
- 布尔字段以 `Is/Has/Can` 开头：`IsCompleted`

### 5.4 其他命名

- 提交相关标识：英文小写 + 连字符，如 `git-commit`、`project-wizard`
- 资源键（resx）：`Section_Item` 形式，如 `Settings_BlurStrength`
- 分支名：见第八章

## 六、代码规范

### 6.1 通用规则

- 遵循 [Microsoft C# Coding Conventions](https://learn.microsoft.com/dotnet/csharp/fundamentals/coding-style/coding-conventions)
- 使用 `.editorconfig` 统一缩进、换行、命名风格，提交时编辑器自动应用
- 文件编码 UTF-8 with BOM
- 缩进：4 个空格，不使用 Tab
- 每行不超过 120 字符

### 6.2 强制要求

- 公共 API（public 类、方法、属性）必须有 XML 文档注释
- 异步方法使用 `async/await`，禁止 `Task.Result` / `.Wait()` 阻塞
- 禁止吞异常（`catch { }`），至少记录日志或向上抛出
- 数据库、文件、Git 等外部操作必须有异常处理与用户提示
- 不得使用已废弃的 API

### 6.3 分层与依赖

- ViewModel 不得直接引用 Repository，必须通过 Service 或接口
- Service 之间允许调用，但禁止循环依赖
- 跨层通信优先用接口 + 依赖注入
- UI 线程相关操作必须回到 UI 线程更新（使用 `Dispatcher` 或 `SynchronizationContext`）

### 6.4 可测试性

- 业务逻辑可脱离 UI 与数据库单元测试（依赖注入 + Mock）
- 关键业务（立项 CRUD、导出导入、Git 操作、提醒调度）必须有自动化测试

### 6.5 注释

- 解释"为什么"而不是"做什么"
- 复杂逻辑、算法、业务规则必须写注释
- 临时绕过的代码必须标注 `// HACK:` 或 `// TODO:` 并附责任人

## 七、UI 组件化与高斯模糊规范（组件复用）

### 7.1 核心思想：样式先集中，控件再复用

项目要求控件具有**高斯模糊、圆角、现代动画、平滑动画**的视觉风格。为避免在每一个窗口里重复写模糊参数、圆角半径、阴影与动画资源，必须遵循"**样式先集中、控件再复用**"的原则：

1. **所有视觉样式先定义在全局资源字典里**，不在 XAML 页面内联写死；
2. **模糊等高频组合效果封装成可复用组件**（自定义控件 / 资源键 / 附加属性）；
3. 页面只做一件事——**引用资源字典里现成的样式或组件**，不再写模糊、圆角、动画细节。

> 一句话规则：**页面里不该出现 `<BlurEffect Radius="..."/>` 这种内联写法，也不该在页面内重复定义模糊层结构。**

### 7.2 样式资源字典的组织

所有全局样式统一放到 `src/SOrtus/Resources/Styles/`，按控件类型拆分，再通过一个总入口合并。

```
src/SOrtus/Resources/
├── Themes/                      # 浅色/深色主题（色板、画刷）
│   ├── Light.xaml
│   ├── Dark.xaml
│   └── Theme.xaml               # 主题总入口（运行时整本替换，实现换肤）
└── Styles/                      # 全局样式与控件模板
    ├── Colors.xaml              # 色板（模糊强度、透明度、覆盖层色值）
    ├── Sizes.xaml               # 圆角半径、间距、模糊半径档位
    ├── Animations.xaml          # 公共动画资源（Storyboard、EasingFunction）
    ├── Brushes.xaml             # 模糊用画刷、覆盖层画刷
    ├── Controls.Base.xaml       # Border/Panel/Window 通用基础样式
    ├── Controls.Button.xaml
    ├── Controls.Card.xaml       # 卡片（模糊面板常用）
    ├── Controls.Dialog.xaml     # 弹窗/浮层（模糊遮罩常用）
    ├── Blur.xaml                # ★ 高斯模糊相关样式与模板（本节核心）
    └── Styles.xaml              # 样式总入口（合并上述所有字典）
```

**加载顺序有讲究**（`Styles.xaml` 内容）：基础层必须先于样式层，否则样式层引用的资源还不存在。

```xml
<ResourceDictionary xmlns="..." xmlns:x="...">
    <ResourceDictionary.MergedDictionaries>
        <!-- 基础层：颜色 / 圆角 / 画刷 -->
        <ResourceDictionary Source="Colors.xaml"/>
        <ResourceDictionary Source="Sizes.xaml"/>
        <ResourceDictionary Source="Brushes.xaml"/>
        <!-- 公共动画 -->
        <ResourceDictionary Source="Animations.xaml"/>
        <!-- 控件样式层 -->
        <ResourceDictionary Source="Controls.Base.xaml"/>
        <ResourceDictionary Source="Controls.Button.xaml"/>
        <ResourceDictionary Source="Controls.Card.xaml"/>
        <ResourceDictionary Source="Controls.Dialog.xaml"/>
        <!-- 高斯模糊组件 -->
        <ResourceDictionary Source="Blur.xaml"/>
    </ResourceDictionary.MergedDictionaries>
</ResourceDictionary>
```

在 `App.xaml` 里只引用这一个总入口，整个应用即可使用：

```xml
<Application.Resources>
    <ResourceDictionary>
        <ResourceDictionary.MergedDictionaries>
            <ResourceDictionary Source="Resources/Themes/Theme.xaml"/>
            <ResourceDictionary Source="Resources/Styles/Styles.xaml"/>
        </ResourceDictionary.MergedDictionaries>
    </ResourceDictionary>
</Application.Resources>
```

### 7.3 模糊强度档位（统一枚举，禁止各页乱填数值）

模糊半径不得硬编码在页面里，统一在 `Sizes.xaml` 定义为命名档位：

```xml
<!-- Sizes.xaml -->
<x:Double x:Key="BlurRadiusNone">0</x:Double>
<x:Double x:Key="BlurRadiusSubtle">6</x:Double>     <!-- 轻微层次：卡片底部 -->
<x:Double x:Key="BlurRadiusNormal">12</x:Double>    <!-- 默认：面板/卡片 -->
<x:Double x:Key="BlurRadiusStrong">20</x:Double>    <!-- 强：弹窗遮罩 -->
<x:Double x:Key="BlurRadiusOverlay">30</x:Double>   <!-- 浮层/全屏遮罩 -->
```

配套颜色与画刷（`Brushes.xaml`）：

```xml
<Color x:Key="BlurOverlayLightColor">#40FFFFFF</Color>   <!-- 浅色主题：白色覆盖 -->
<Color x:Key="BlurOverlayDarkColor">#40222222</Color>    <!-- 深色主题：深色覆盖 -->
<SolidColorBrush x:Key="BlurOverlayBrush"
                 Color="{DynamicResource BlurOverlayLightColor}"/>
```

**注意**：模糊覆盖层色值、透明度的语义随主题变化，因此一律用 `DynamicResource` 引用，`Blur.xaml` 里的样式不要写死颜色。

### 7.4 高斯模糊的实现约定

WPF 实现"控件背景模糊"有两条路线，本项目约定如下。

#### 7.4.1 首选：自定义附加属性组件（复用性最好）

新建 `src/SOrtus/Controls/BlurPanel.cs`，提供以下附加属性：

| 附加属性 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `BlurPanel.EnableBlur` | `bool` | `false` | 是否启用背景模糊 |
| `BlurPanel.BlurRadius` | `double` | `12` | 模糊半径（对应 7.3 的档位） |
| `BlurPanel.OverlayOpacity` | `double` | `0.5` | 模糊层之上覆盖层的透明度 |
| `BlurPanel.Background` | `Brush` | `null` | 覆盖层画刷，缺省取主题画刷 |

实现要点（必须遵循）：

- 控件内部自行构建"**背景模糊层（VisualBrush + BlurEffect）+ 覆盖层**"两层结构，使用 `Grid` 承载，业务内容放在上层，保证**模糊只作用于背景、不模糊内容本身**；
- 在 `Loaded` 与 `SizeChanged` 事件中更新模糊层尺寸，使模糊范围始终贴合控件；
- 模糊半径、覆盖层色值绑定到 `Sizes.xaml` / `Brushes.xaml` 的资源键，主题切换时自动响应；
- 对外暴露的属性即上表四项，业务页面**不允许**再自行添加模糊相关属性。

页面使用方式（一行即可，无需任何内联模糊代码）：

```xml
<Border local:BlurPanel.EnableBlur="True"
        local:BlurPanel.BlurRadius="{StaticResource BlurRadiusNormal}"
        local:BlurPanel.OverlayOpacity="0.5"
        CornerRadius="{StaticResource CornerRadiusMedium}">
    <TextBlock Text="立项信息" .../>
</Border>
```

#### 7.4.2 次选：样式里内联 BlurEffect（仅极简单场景）

仅在"整块内容统一模糊、无需分层"的场景下允许在样式内写 `<BlurEffect/>`，且**必须在 `Blur.xaml` 里定义、通过资源键引用**：

```xml
<!-- Blur.xaml -->
<BlurEffect x:Key="BlurEffectNormal"
            Radius="{StaticResource BlurRadiusNormal}"
            KernelType="Box"
            RenderingBias="Performance"/>
```

使用：

```xml
<Border Effect="{StaticResource BlurEffectNormal}">...</Border>
```

#### 7.4.3 内核选型（性能相关，写死）

| 场景 | 内核 | 理由 |
| --- | --- | --- |
| 静态面板、背景、卡片 | `KernelType="Gaussian"` | 视觉过渡平滑、自然 |
| 动态内容、实时跟随、频繁刷新区域 | `KernelType="Box"`，`RenderingBias="Performance"` | 计算量约 O(n)，避免掉帧 |
| 动画过程中 | 见 7.7 | 不得逐帧重算模糊 |

### 7.5 全局样式与组件的引用规则

| 场景 | 引用方式 | 说明 |
| --- | --- | --- |
| 画刷、色值、尺寸 | `{DynamicResource BlurOverlayBrush}` | 主题相关，必须 Dynamic |
| 静态几何、固定色值 | `{StaticResource BlurEffectNormal}` | 编译期解析，写错直接报错 |
| 具名样式 | `Style="{StaticResource BlurCardStyle}"` | 需设置 `x:Key` |
| 隐式样式 | 不写 `x:Key`，只写 `TargetType` | 自动作用于全应用该类型控件 |

**强制规则**：

1. 模糊相关资源**只允许定义在 `Blur.xaml` 或 `Brushes.xaml`**，其他样式文件不得重复定义同名模糊资源；
2. 新增控件样式时，模糊效果**必须基于现有 `BlurPanel` 或 `Blur.xaml` 里的资源**，不得另起一套实现；
3. 同名资源冲突时"后合并者胜"，因此 `Blur.xaml` 的位置一经确定不得随意调整顺序；
4. 每个 `ResourceDictionary` 默认共享单例，若某资源必须每次新建实例，显式标注 `x:Shared="False"`。

### 7.6 圆角、动画也一并全局化（避免只抽模糊、其他地方仍散落）

- **圆角半径**：统一在 `Sizes.xaml` 定义 `CornerRadiusSmall / Medium / Large / Pill`，控件用 `CornerRadius="{StaticResource CornerRadiusMedium}"`；
- **公共动画**：进入 / 退出 / 悬浮的 Storyboard 统一放在 `Animations.xaml`，通过资源键引用，禁止页面内重复定义相同缓动；
- **隐式样式**：通用控件（如所有 `Border` 类卡片）优先使用无 `x:Key` 的隐式样式，减少页面样板代码。

### 7.7 性能红线（模糊是性能热点，必须守）

1. **模糊半径默认不超过 20**；弹窗遮罩等大面积区域确有需要时例外，但需说明；
2. **禁止给 `ItemsControl` / `ListView` / `DataGrid` 的每一项单独套模糊**——列表项数量不可控，会造成大面积重绘与严重掉帧；模糊只允许作用于列表外层容器或选中项；
3. **禁止把动画作用在 `BlurEffect.Radius` 上逐帧重算**；若需动态模糊，使用 `BitmapCache` 缓存静态层，动画只改 `Opacity` / `Transform`；
4. **静态层加 `CacheMode="BitmapCache"`**：模糊结果缓存起来，避免每帧重新卷积；动画层与静态层必须分层，不要把 Effect 加在动画层上；
5. **窗口级别**：禁止同时开启 `AllowsTransparency="True"` 与大面积模糊，后者会强制走软件渲染、失去 GPU 加速；
6. 新增大面积模糊区域时，必须在目标机器上跑一次渲染耗时验证（见 7.9）。

### 7.8 主题与模糊的联动

深色 / 浅色主题的切换通过**整本替换 `Application.Current.Resources.MergedDictionaries` 中的主题字典**实现。由于模糊覆盖层色值、`BlurOverlayBrush` 等都通过 `DynamicResource` 引用主题画刷，换肤时所有模糊控件自动重新解析、无需重启应用。

`Theme.xaml` 中提供 `Dark` / `Light` 两个主题字典，资源键**完全一一对应**（键名、类型保持一致），缺失的键会导致切换后模糊层显示异常。

### 7.9 验收标准（本组件化的提测清单）

**功能**

1. `BlurPanel` 的 `EnableBlur / BlurRadius / OverlayOpacity / Background` 四个附加属性均可正常读写，缺省值与 7.4.1 一致；
2. 页面使用该组件后，**XAML 内不出现 `<BlurEffect>` 内联标签**，模糊半径、覆盖层均由资源字典提供；
3. 模糊只作用于背景层，控件内的文字、图标、子控件**不被模糊**；
4. 控件尺寸变化时（窗口缩放、内容增减），模糊层自动跟随，不留空白或溢出。

**复用性**

5. 同一套模糊样式可在至少 3 类控件（卡片、弹窗、列表容器）上直接引用，无需复制 XAML；
6. 修改 `Sizes.xaml` 中 `BlurRadiusNormal` 一个值，全应用所有引用该档位的控件**同时**更新，无需逐页修改。

**主题**

7. 浅色 / 深色切换时，所有模糊控件的覆盖层色值随之变化，无需重启应用；两个主题字典的资源键**完全一致**。

**性能**

8. 主窗口含默认模糊面板时，窗口缩放、列表滚动保持流畅（目标 60 FPS，无肉眼可见掉帧）；
9. 立项列表（`ListView`）的每一项**不带**独立模糊效果，模糊只作用于外层容器；
10. 静态模糊层已启用 `BitmapCache`，且不存在"动画改模糊半径"的写法。

**回归**

11. 上述验收通过后，不得出现"页面内另写一份模糊实现"的新增代码；代码评审中凡发现内联 `<BlurEffect>` 一律退回。

## 八、Git 提交与推送约定

### 8.1 提交信息格式

采用 [Conventional Commits](https://www.conventionalcommits.org/) 规范，格式：

```
<type>(<scope>): <subject>

<body>

<footer>
```

- **type**（必填）：提交类型
- **scope**（可选）：影响范围，如 `project`、`git`、`ui`、`docs`、`build`
- **subject**（必填）：简短描述，不超过 72 字符，首字母小写，结尾不加句号
- **body**（可选）：说明动机与实现要点，与 subject 空一行
- **footer**（可选）：关联 issue、BREAKING CHANGE、作者等

### 7.2 type 类型表

| type | 含义 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat(project): 新增剪辑项目立项向导` |
| `fix` | 缺陷修复 | `fix(git): 修复非仓库路径下崩溃` |
| `docs` | 文档变更 | `docs: 更新开发文档架构章节` |
| `style` | 代码格式（不影响逻辑） | `style: 统一缩进与命名` |
| `refactor` | 重构 | `refactor(repo): 抽取基类仓储` |
| `perf` | 性能优化 | `perf(list): 虚拟化立项列表` |
| `test` | 测试相关 | `test(git): 补充推送失败用例` |
| `build` | 构建、打包、依赖 | `build: 升级 SQLite 驱动版本` |
| `ci` | CI 流程 | `ci: 添加打包流水线` |
| `chore` | 杂项（不属以上） | `chore: 清理无效引用` |
| `revert` | 回退 | `revert: feat(project): 撤销版本发行模块` |

### 7.3 scope 常用取值

`project`（立项）、`clip`（剪辑）、`todo`（待办）、`ui`（界面）、`theme`（主题/模糊/动画）、`i18n`（多语言）、`git`、`remind`（提醒）、`data`（导出导入备份）、`db`（数据库）、`docs`、`build`、`release`、`repo`、`service`、`test`。

```

BREAKING CHANGE: 数据库立项表新增剪辑字段，需执行迁移脚本 v3。
```

### 7.5 提交纪律

- **原子提交**：一次提交只做一件事，便于 review 与回退
- **可编译**：每个提交都必须能编译通过，禁止提交半成品破坏构建
- **不混入无关改动**：不要把格式化、重构、功能写进同一个提交
- **不提交敏感信息**：密钥、令牌、个人路径、内部链接一律不入仓
- **提交前自查**：`git status`、`git diff`，确认只包含预期改动

### 7.6 推送规则

- 推送前先 `git pull --rebase`（或合并最新主干），解决冲突后再推
- 禁止强制推送（`git push --force`）到 `main` / `master` / `release/*` 分支
- 特性分支的强制推送仅在个人分支且团队知悉时使用
- 推送后立即确认 CI/构建状态
- 一个 PR 对应一个逻辑变更，不混合多个无关功能

### 7.7 提交频率建议

- 小步快跑：完成一个可编译、可验证的小功能即可提交
- 不要积累大量改动后一次性提交
- 阶段性里程碑必须有一个清晰的提交记录点

## 九、分支管理

### 8.1 分支模型（简化 GitFlow）

```
main              # 主干，始终可发布，受保护
├── develop       # 开发集成分支
├── feature/*     # 功能分支
```

### 8.2 分支命名

| 分支 | 命名格式 | 示例 |
| --- | --- | --- |

| 修复 | `fix/<issue>-<描述>` | `fix/45-git-push-null` |
| 发版 | `release/<版本号>` | `release/0.2.0` |
| 热修 | `hotfix/<版本号>-<描述>` | `hotfix/0.2.1-typo` |

### 8.3 分支规则

- `main` 与 `develop` 受保护，只能通过 PR 合并

### 8.4 PR 要求

- 必须通过 CI 构建与测试
- 至少一个 Reviewer 审批（本人不得自审）
- 合并前解决所有冲突、删除源分支

## 十、发行版与版本约定

### 9.1 版本号规范

采用 [语义化版本 SemVer 2.0.0](https://semver.org/lang/zh-CN/)：**主版本.次版本.修订号**（如 `1.2.3`）。

| 位 | 名称 | 递增时机 |
| --- | --- | --- |
| 主版本（Major） | 主版本号 | 做了不兼容的 API 或数据库结构变更 |
| 次版本（Minor） | 次版本号 | 以向后兼容的方式添加了功能 |
| 修订号（Patch） | 修订号 | 向后兼容的问题修复 |

**预发版本**：`1.0.0-alpha.1`、`1.0.0-beta.2`、`1.0.0-rc.1`（标识符按 `alpha → beta → rc → 正式` 推进）。

### 9.2 版本与路线图对应

| 路线图称呼 | 语义化版本号 | 说明 |
| --- | --- | --- |
| MVP | `0.1.0` | 首个里程碑，API 未稳定，主版本为 0 |
| 1.1 | `0.2.0` | 剪辑项目 |

| 1.3 | `0.4.0` | 视觉与多语言 |

| 正式版 | `1.0.0` | 首个稳定正式版 |
| 正式版之后 | `1.x.y` / `2.x.y` | 遵循 SemVer 递增 |

> 主版本为 `0` 时（`0.x.y`）表示项目处于初始开发阶段，任何版本变更都可能引入不兼容，不保证 API 稳定性。到达 `1.0.0` 后严格遵守 SemVer。

### 9.3 版本号管理

- 版本号**单一来源**：集中在 `Directory.Build.props` 或 `version.props` 管理，禁止散落在多处

2. 在 release 分支完成最终缺陷修复、更新版本号、更新 `CHANGELOG.md`、更新 `README` 截图

5. 合并 release 分支回 `develop`

## 十一、依赖与第三方组件

### 10.1 引入原则

- 优先使用 .NET 官方库与稳定社区库
- 引入新依赖前评估：许可证、活跃度、体积、是否纯本地（无网络依赖）
- 禁止引入与项目约定冲突的组件（如含遥测、后台服务的库）

### 10.2 依赖管理

- 统一通过 `.csproj` 的 `PackageReference` 管理，版本固定（不使用浮动版本）
- 依赖清单在 `docs/开发文档.md` 中登记（名称、版本、用途、许可证）
- 升级依赖需评估兼容性并做回归测试

### 10.3 许可证合规

- 所有第三方依赖的许可证必须在文档中声明
- 使用 GPL 类强 Copyleft 许可证的组件需专项评审
- MIT 项目使用 MIT/BSD/Apache 2.0 类兼容许可证的库一般无障碍

## 十二、构建与打包

### 11.1 构建

- 提供一键构建脚本 `build/build.ps1`
- 构建命令统一、可重复：`dotnet build`、`dotnet publish`
- 构建输出统一到 `artifacts/` 目录（已在 `.gitignore` 忽略）
- 警告视为错误（关键警告等级可配置），构建零警告零错误

### 11.2 打包

- 产出两种形式：**安装包**（`.exe`，带安装引导）与**便携版**（`.zip`，解压即用）
- 两种产物均仅面向 Windows x64
- 安装包必须包含：应用、依赖运行时（自包含发布）、快捷方式、卸载入口
- 便携版必须可放到任意目录直接运行，数据文件与程序同目录或用户目录可配置

### 11.3 自包含与单文件

- 发版采用自包含发布（`-p:PublishSelfContained=true`），目标 `win-x64`
- 是否单文件（`PublishSingleFile`）由打包脚本参数控制，默认不强制
- 不依赖用户机器预装 .NET 运行时

### 11.4 构建产物清单

每次发版 `artifacts/` 应包含：

```
SOrtus-<version>-win-x64.exe
SOrtus-<version>-win-x64-portable.zip
SOrtus-<version>-win-x64-symbols.zip   # 可选
checksums.txt                          # 各产物 SHA256
```

## 十四、约定红线（禁止项）

以下为项目硬性禁止，违反即要求整改：

1. **禁止任何远端接口与后端服务器**：本项目纯本地，不得引入 API 调用、云服务、后台服务
2. **禁止收费、会员、广告模块**：不得植入付费墙、订阅、推广内容
3. **禁止遥测与数据上报**：不采集、不上传用户数据与使用行为
4. **禁止提交敏感信息**：密钥、令牌、个人路径、内部链接
5. **禁止提交编译产物**：`bin/`、`obj/`、`artifacts/` 已在 `.gitignore`
6. **禁止绕过提交规范**：不使用无意义的提交信息（如 `update`、`fix bug`）
7. **禁止跳过 PR 审查**：直接推送到受保护分支
8. **禁止版本号不一致**：程序集、文件、安装包、关于页版本必须统一
9. **禁止破坏性变更不打 Migrations**：数据库结构变更必须有迁移脚本
10. **禁止文档漂移**：功能改动后不更新相关文档
11. **禁止大文件入仓**：单个文件超过 10MB 需评估，二进制源文件优先不入仓
12. **禁止个人风格凌驾约定**：本文档未覆盖处才允许个人判断，不得反向推翻既有规范
